# Local autonomous campaign — 2–3 November 2026

Start or resume with `npm run official:campaign`. It uses the existing project venv and the local viewer service on port 8766. The dashboard is [local campaign](http://127.0.0.1:8766/ui/campaign.html). Password: `KartBlitzPass`. The deadline is absolute: training stops at **03:00 Tuesday 3 November, Sydney**, validation ends by **03:45**, and a separate watchdog begins emergency cleanup at **03:59**, before the **04:00 hard stop**. Restarting does not extend the deadline.

The runner starts one independent CUDA learner, then tests up to four. Each uses 64 cars, three physics workers and one Torch thread. After stable 120-second windows it retains an additional learner only for at least 10% aggregate throughput improvement. A slower job is checkpointed and stopped, then its task can resume later. GPU utilization alone never justifies more jobs.

Whole-device dedicated VRAM is capped at 7 GiB, system RAM at 95%; new jobs require a little more headroom than those ceilings. CPU percentage does not independently prevent parallelism. Windows PDH tracks shared GPU memory for the learners and their actual child processes. A tiny 4 KiB CUDA tensor measured 76 MiB of normal WDDM shared bookkeeping on this laptop; the guard allows 96 MiB per learner, then stops learners if additional shared usage reaches 64 MiB. Both raw usage and excess are recorded. If that counter is unavailable, concurrency cannot increase. CUDA tensor allocation is also bounded per process. The simulations, optimizer bookkeeping and recordings still require ordinary RAM. No model offload to shared system RAM is implemented. Other applications remain outside the runner's control.

Training waits on battery, pauses for resource faults and low free disk space, and temporarily prevents system sleep only on mains power. No permanent power/fan/clock settings are changed. Existing recordings are retained. New training recordings stop at 45 GiB, leaving up to 5 GiB of the 50 GiB campaign allowance for validation. If that training cap is reached, the campaign proceeds to final checks early. Source files are snapshotted and fingerprinted; changing training/game sources during a run pauses collection and blocks approval until reviewed.

Priority is all-track Extreme solo learning, then racecraft, then independent optimization challengers. Only after that coverage is adequate are other difficulties scheduled. Tasks run in approximately 20-minute resumable chunks. Two retries are allowed after a worker fault. Closed browser/chat windows do not stop the runner; the dashboard's **Save and pause all** releases learner resources, **Resume campaign** resumes queued tasks, and **Stop campaign** ends the controller. A process/computer restart requires rerunning the start command; checkpoints and the remaining task queue persist.

Each active slot gets a labeled Edge/browser window. Windows are reused between tasks. A recorded lap plays to its end before automatic handover; failed/interrupted attempts are labeled. The camera is a replay of a recorded attempt, while the batch map contains current samples. Explicit Stop freezes playback. Battery percentage, actual ERS/DRS activation and DRS-zone status appear over the normal game camera.

## Data retained

Each job has a normal 32-character run ID under `ml_training/runs/official/`. Its spec, full effective config, source fingerprint, status, worker log, optimizer checkpoints and browser policy package are retained. `attempts.jsonl.gz` contains independent compressed members, with `attempt-index.jsonl` providing outcomes, times and byte offsets. Every 20 Hz point includes position/heading, speed, controls, reward, track progress, checkpoint, battery charge, actual ERS/DRS state, DRS availability/zone, tyre state and opponent poses. Worker/environment IDs disambiguate parallel cars. Interrupted fragments are stored with `interrupted: true` and never counted as completed laps. This supports reconstructing selected laps or overlaying 1,000 attempts on the same track without saving video files.

Campaign state/events, resource samples, source snapshots and held-out evaluation recordings live under `ml_training/runs/campaign/current/`. Native browser validation also saves compressed trajectories with energy/opponent telemetry. No recordings are automatically deleted.

## Approval and export

Solo, overtaking, defending, recovery and mixed traffic are evaluated separately. Held-out headless tests use battery-state variation and seeded scenarios. Native browser checks compare Legacy and candidate driving with actual starts, battery states, multi-lap races and matched traffic/recovery cases. Native near-contact events and conservative defensive reversal flags are proxies, not perfect blame attribution or a complete F1 rulebook. Cases and failures remain available for inspection.

Only candidates passing the declared reliability, racecraft, contact, native pace and defensive checks qualify. Candidates more than 3% slower than an evaluated solo baseline are rejected for promotion. Qualifying champions are merged into per-track packages under **`ai-models/approved/`**, with a validation manifest. Copies appear in the local AI Models catalog for manual activation. Other candidates remain in the run archive. This does not claim global optimality, human/WR pace, or complete coverage of all difficulties. Wet weather and upgrades are outside this campaign.

**No git commit, push, remote upload or automatic driver activation is performed.** Approved exports remain uncommitted files in the local repository. The legacy controller stays available.
